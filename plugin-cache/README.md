# @fastify/response-cache

Fastify plugin for response caching with ETag support and LRU eviction.

## Features

- **Zero runtime dependencies** - LRU cache implemented using JavaScript Map, ETag generation uses `node:crypto` (built-in)
- **Route-level opt-in** - Only cached routes are affected by the plugin
- **ETag support** - Automatic weak ETag generation and conditional request handling (If-None-Match → 304)
- **TTL and LRU eviction** - Time-based expiry + size-based eviction with least-recently-used strategy
- **Cache-Control parsing** - Respects standard directives (no-store, private, max-age, s-maxage, no-cache)
- **Manual invalidation API** - Purge by exact key, URL prefix, or clear all

## Installation

```bash
npm install @fastify/response-cache
```

## Usage

### Basic Setup

```javascript
const fastify = require('fastify')()
const cachePlugin = require('@fastify/response-cache')

// Register the plugin
await fastify.register(cachePlugin, {
  maxItems: 1000,        // Max cached responses (default: 1000)
  ttl: 60000,            // Default TTL in milliseconds (default: 60000 / 1 minute)
  methods: ['GET'],      // HTTP methods to cache (default: ['GET'])
  vary: []               // Global Vary headers to include in cache key (default: [])
})

// Opt-in to caching per route
fastify.get('/users', {
  config: {
    cache: true  // Use default TTL
  }
}, async (request, reply) => {
  return await db.getUsers()
})

// Custom TTL and Vary headers per route
fastify.get('/products', {
  config: {
    cache: {
      ttl: 30000,           // Override default TTL for this route
      vary: ['Accept']      // Additional Vary headers for this route
    }
  }
}, async (request, reply) => {
  return await db.getProducts()
})
```

### Cache Key Derivation

The cache key is derived from:
1. HTTP method
2. URL (path + query string)
3. Configured Vary headers (both global and route-level)

**Format:** `method|url|vary_header_values`

**Examples:**
- `GET|/users|` (no vary headers)
- `GET|/users|accept:application/json` (with Accept header)
- `GET|/users?page=2|accept:application/json` (with query string)

Different query strings or Vary header values create separate cache entries.

### Cache Invalidation API

```javascript
// Purge specific entry by exact cache key
fastify.cache.purge('GET|/users|')

// Purge all entries matching URL prefix
fastify.cache.purgeByPrefix('/users')

// Clear entire cache
fastify.cache.clear()

// Get cache statistics
const stats = fastify.cache.stats()
// { items: 42, maxItems: 1000, hits: 150, misses: 30 }
```

### ETag and Conditional Requests

The plugin automatically generates weak ETags for all cached responses:

- **Format:** `W/"16-char-hex"` (SHA-256 hash, truncated to 16 characters)
- **Conditional requests:** If client sends `If-None-Match` header matching the ETag, the plugin responds with `304 Not Modified` (no body)
- **Bandwidth savings:** 304 responses skip the response body entirely

### Cache-Control Header Support

#### Response Cache-Control Directives

| Directive    | Behavior                                                         |
|--------------|------------------------------------------------------------------|
| `no-store`   | Do not cache the response                                        |
| `private`    | Do not cache (server-side cache is shared)                       |
| `no-cache`   | Cache but always revalidate (immediate expiry, ETag still works) |
| `max-age=N`  | Override route TTL with N seconds                                |
| `s-maxage=N` | Override route TTL with N seconds (takes priority over max-age)  |

#### Request Cache-Control Directives

| Directive  | Behavior                                                     |
|------------|--------------------------------------------------------------|
| `no-cache` | Bypass cache, run handler, but store the fresh response      |
| `no-store` | Bypass cache, run handler, do NOT store the response         |

### Response Headers

The plugin adds the following headers:

- **`ETag`**: Weak ETag (e.g., `W/"a3f7c9e1b2d4e8f6"`)
- **`X-Cache`**: Status indicator
  - `HIT` - Response served from cache
  - `MISS` - Response generated by handler and stored
  - `BYPASS` - Cache bypassed due to request Cache-Control

## Hook Ordering and Plugin Registration

### Critical: Register After Authentication

**The cache plugin MUST be registered AFTER authentication/authorization plugins.**

If you register the cache plugin before authentication, **cache hits will bypass authentication checks**, creating a serious security vulnerability.

#### ✅ Correct Order

```javascript
const fastify = require('fastify')()

// 1. Register authentication first
await fastify.register(require('@fastify/jwt'), { secret: 'supersecret' })
await fastify.register(require('@fastify/auth'))

fastify.addHook('onRequest', async (request, reply) => {
  await request.jwtVerify()  // Verify JWT on every request
})

// 2. Register cache plugin AFTER authentication
await fastify.register(require('@fastify/response-cache'), {
  maxItems: 1000,
  ttl: 60000
})

// 3. Define routes
fastify.get('/protected', {
  config: { cache: true }
}, async (request, reply) => {
  return { user: request.user }
})
```

**Why this works:**
- First request: `onRequest` hook runs authentication → handler executes → `onSend` hook stores response
- Second request: `onRequest` hook runs authentication first → if valid, cache check happens → if cache hit, serve cached response
- **Authentication always runs before cache check**

#### ❌ Incorrect Order (Security Risk)

```javascript
// WRONG: Cache registered before authentication
await fastify.register(require('@fastify/response-cache'))
await fastify.register(require('@fastify/jwt'))
```

**Why this is dangerous:**
- First request: Authentication runs → response cached
- Second request: **Cache hit bypasses authentication** → unauthenticated user gets cached response
- **Severe security vulnerability**

### Hook Execution Order

The cache plugin uses two Fastify hooks:

1. **`onRequest`** - Checks cache for hits, serves cached responses (including 304)
2. **`onSend`** - Stores successful responses after handler execution

**Hooks run in registration order:**

```
→ onRequest (authentication plugins)
→ onRequest (cache plugin) ← checks cache
→ Route handler (if cache miss)
→ onSend (cache plugin) ← stores response
→ onSend (other plugins)
```

### Best Practices

1. **Always register cache after authentication/authorization**
2. **Never cache authenticated responses if they differ per user** - Use Vary headers or disable caching
3. **Use route-level opt-in** - Only enable caching on routes that are safe to cache
4. **Consider Vary headers** - If responses differ by Accept, Authorization, etc., include those headers in `vary`
5. **Monitor cache stats** - Use `fastify.cache.stats()` to track hit rate and performance

## Technical Implementation

### LRU Cache (Map-based)

The plugin implements an LRU cache using JavaScript's built-in `Map`:

- **O(1) lookup** - Fast key-based retrieval
- **Insertion order** - `Map` maintains insertion order (V8 guarantee)
- **LRU strategy** - On access, entry is deleted and re-inserted to move it to the end (most recent)
- **Eviction** - When full, `map.keys().next().value` gives the oldest key for eviction
- **Lazy expiry** - Expired entries are cleaned up on access, not via timers

Each cache entry stores:
```javascript
{
  body: string | object,    // Response body
  statusCode: number,        // HTTP status code
  headers: object,           // Response headers (Content-Type minimum)
  etag: string,              // Generated weak ETag
  expiry: number             // Timestamp (Date.now() + ttl)
}
```

### ETag Generation

ETags are generated using `node:crypto` (built-in):

```javascript
const { createHash } = require('node:crypto')

function generateETag (body) {
  const hash = createHash('sha256')
    .update(typeof body === 'string' ? body : JSON.stringify(body))
    .digest('hex')
    .slice(0, 16)
  return 'W/"' + hash + '"'
}
```

- **Algorithm:** SHA-256
- **Format:** Weak ETag (`W/"..."`)
- **Length:** 16 hex characters (truncated)
